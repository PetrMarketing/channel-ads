# MAX Marketing: REST API для интеграций

Рабочий сервер Петра: `https://itcakes.ru`. На отдельном клиентском проде замените домен своим.
Все пути уже включают `/api`: не добавляйте этот префикс дважды.

## Документация и загрузки

- [Полный список всех методов по разделам](CATALOG.md).
- [Полная OpenAPI-спецификация](openapi.json).
- [Коллекция Postman](postman_collection.json).
- [Машиночитаемый каталог](catalog.json).
- Живой Swagger: `/api/integration/docs`.
- Живая схема: `/api/integration/openapi.json`.
- Отдельный API каждого раздела: `/api/integration/openapi/{module}.json` — например `shop`, `services`, `pins`, `funnels`, `content`, `ai-design`, `paid-chats`.
- Страница выдачи ключей и поиска методов: `/integrations`.

Это интеграционный доступ к существующим обработчикам, а не вторая копия бизнес-логики.
Функциональность, тарифы, сроки выполнения и ограничения те же, что в интерфейсе.
Версия каталога 1.0.0; URL существующего API сохранены. Это не обещание неизменности всех legacy-контрактов: перед обновлением сверяйте схемы.

## Ключи и права

Войдите в сервис → **API и интеграции** → задайте название, срок (1–365 дней) и разделы → **Создать ключ**.
Ключ `mmk_…` показывается один раз. В БД хранится только SHA-256 от случайного 256-битного секрета.
Лимит — 20 активных ключей на аккаунт. Отзыв применяется к следующим запросам сразу; уже выполняющийся запрос не отменяется.

```http
Authorization: Bearer mmk_ВАШ_КЛЮЧ
```

Храните секрет в серверном secret manager / переменной окружения. Не публикуйте в браузере, Git, URL или логах.
Права по каналам проверяет тот же серверный код, что для пользовательской сессии. Дополнительно ключ ограничен выбранными разделами.
`modules: ["*"]` разрешает все пользовательские разделы, включая новые. Для минимальных прав выбирайте явный список, например `["channels", "pins", "funnels"]`.
Ключ не ограничен одним каналом: он видит каналы владельца и каналы, доступные ему как сотруднику, в пределах штатных разрешений.

В каталоге указаны разные режимы доступа:

| Доступ | Требования |
| --- | --- |
| `user` | API-ключ либо пользовательский JWT; проверки канала и тарифа сохраняются |
| `session-jwt` | Только пользовательский JWT после входа: выпуск, просмотр списка и отзыв ключей |
| `admin` / `superadmin` | Отдельный JWT администратора платформы, не пользовательский ключ |
| `metrics-key` | Отдельный `X-API-Key` из служебного `METRICS_API_KEY` |
| `custom-or-public` | Публичная операция либо специальная проверка внутри обработчика: MAX/TG initData, подпись вебхука, платёжный протокол и т. п. |

API-ключ не может менять привязку аккаунта через `/api/auth/*` (кроме чтения `/api/auth/me`), выдавать другие ключи или становиться администратором.
Разделение защищает существующие границы доступа; это не аудит всех старых обработчиков на межклиентские уязвимости.

Управление ключами через API с **JWT пользовательской сессии**:

```http
POST /api/integration/keys
Content-Type: application/json
Authorization: Bearer USER_SESSION_JWT

{"name":"Моя интеграция","expires_in_days":90,"modules":["channels","pins","funnels"]}
```

Ответ `201`: `{"success":true,"key":"mmk_…","metadata":{...},"warning":"…"}`.
`GET /api/integration/keys` возвращает только метаданные и префиксы, не секреты и не хеши.
`DELETE /api/integration/keys/{key_id}` отзывает собственный ключ; повторный отзыв безопасен.

## Начало работы

Следующие примеры предполагают серверные переменные `MM_API_KEY` и `MM_CHANNEL_CODE`.

```bash
curl --fail-with-body 'https://itcakes.ru/api/channels/' \
  -H "Authorization: Bearer $MM_API_KEY"
```

Из ответа возьмите `tracking_code` нужного канала. `{tc}` и `{tracking_code}` в маршрутах — этот строковый код, **не** числовой ID канала/MAX-чата.
ID поста, шага, лид-магнита, товара и т. п. берите из ответа создания или списка соответствующей сущности, не конструируйте самостоятельно.

### Лид-магнит с файлом

Создание принимает **multipart**, даже если прикреплённого файла нет.

```bash
curl --fail-with-body "https://itcakes.ru/api/pins/$MM_CHANNEL_CODE/lead-magnets" \
  -H "Authorization: Bearer $MM_API_KEY" \
  -F 'title=Чек-лист' -F 'message_text=Ваш материал готов!' \
  -F 'file=@checklist.pdf'
```

Список: `GET /api/pins/{tc}/lead-magnets`. Закрепы и лид-магниты находятся в одном модуле `pins`, но имеют отдельные маршруты и сущности.

### Шаг воронки и изменение порядка

```http
POST /api/funnels/{tc}/{lm_id}/steps
Content-Type: application/json

{"delay_minutes":60,"message_text":"Привет, {name}! Вот следующий шаг."}
```

С изображением используйте multipart с полями `delay_minutes`, `message_text`, `file`.
Редактирование: `PUT /api/funnels/{tc}/{lm_id}/steps/{step_id}`.
Перестановка: `POST /api/funnels/{tc}/{lm_id}/steps/reorder`, JSON `{"ids":[3,1,2]}`.
Передайте **все** ID шагов этой воронки ровно по одному в нужном порядке.

### Пост

```http
POST /api/content/{tc}
Content-Type: application/json

{"title":"Новый пост","message_text":"Текст публикации"}
```

Без `scheduled_at` создаётся черновик; указание даты планирует публикацию и может привести к автоматической отправке.
`POST /api/content/{tc}/{post_id}/publish` публикует реальное сообщение.
Для вложений используйте multipart: `file` либо повторяющееся поле `files` (до 10 файлов).
Структуры вроде `inline_buttons` в multipart передаются JSON-строкой; в JSON-теле — объектами/массивами согласно обработчику.
Не выставляйте Content-Type multipart вручную: клиентская библиотека должна добавить boundary.
Прогресс загрузки на клиенте отслеживается по отправленным байтам (XHR upload progress); 100% передачи файла не означает завершение обработки на сервере.

## Основные цепочки по разделам

| Задача | Разделы API и порядок |
| --- | --- |
| Лид-магнит → закреп → прогрев | `pins`: создать лид-магнит, закреп с его ID; `funnels`: создать шаги, настроить задержки, порядок |
| Контент и публикации | `content`: черновики, правка, расписание, publish; `ai-content` / `ai-post`: генерации |
| Рассылка | `broadcasts`: создать, посчитать получателей, send-test, send, читать status/stats |
| Оформление канала | `ai-design`: создать session, заполнить survey, загрузить photo, generate-avatars/descriptions, выбрать, apply |
| Магазин | `shop`: настройки, категории, товары, атрибуты/варианты, изображения, промокоды, заказы и статусы |
| Запись на услуги | `services`: филиалы, категории, услуги, специалисты, расписание, записи и статусы |
| Платные чаты | `paid-chats`: настройки оплаты, тарифы, чаты, участники; `paid-chat-pay`: отдельный покупательский платёжный протокол |
| Сайт | `ai-landing`: проект, генерация, редактирование, публикация в рамках существующих операций |
| Комментарии, опросы, эфиры | `comments`, `polls`, `streams`; публичные mini-app методы имеют собственную авторизацию |
| Привлечение и аналитика | `links`, `track`, `analytics`, `channels`; рекламные пиксели задаются на ссылке |
| Управление аккаунтом | `billing`, `payments`, `referrals`, `notifications`, `clients`, `support`, `onboarding` |
| Административная панель | `admin` с отдельным admin JWT; `metrics` со служебным ключом |
| ИИ-Агент | `ai-agent`: project → brief → source-file/source-url → start → current. Текущая реализация заканчивается первым этапом и awaiting_approval; API не добавляет отсутствующие последующие этапы |

Полный перечень GET/POST/PUT/DELETE для каждой сущности — в [CATALOG.md](CATALOG.md) и отдельных спецификациях.

## Ответы, ошибки и повтор запросов

Legacy API сохраняет существующие форматы: обычно `{"success":true,...}`, но названия полей/обёрток различаются; универсального `data` нет.
Списки могут быть пагинированы только там, где это предусмотрено конкретным методом. Проверяйте query-параметры.
Типичная ошибка: `{"success":false,"error":"…"}`. Ошибки проверки FastAPI/Pydantic могут возвращать `{"detail":[...]}`.

- `401`: отсутствующий, неверный, отозванный или истёкший credential.
- `403`: недостаточно прав или ключ не имеет доступа к разделу.
- `404`: объект не найден/недоступен; не делайте вывод о его наличии у другого клиента.
- `400`/`422`: неверные параметры или недопустимое действие.
- `409`: конфликт, например лимит активных ключей.
- Ошибки тарифа/баланса/провайдера зависят от конкретного обработчика.

Единого Idempotency-Key для старых операций **нет**. Не повторяйте автоматически POST, отправки, оплаты и генерации после таймаута: сначала проверяйте состояние объекта.
Фоновые задачи выполняются существующими механизмами; опрашивайте соответствующие `status`/`current`/списки, где они доступны. Новый API не гарантирует сохранность старых in-process задач при перезапуске.
Не запускайте коллекцию Postman целиком: она содержит реальные DELETE, рассылки, публикации и платные операции. Заполнители намеренно не содержат чужих ID и автоматически исполняемых сценариев.

## Полнота контракта и проверка

Каталог автоматически охватывает все зарегистрированные `/api/*` методы, включённые в схему. Небизнесовые HTML-страницы, HLS/RTMP и `/webhook/max` не выдаются за REST API управления.
Параметры пути, типизированные query/Form/Body и модели берутся из FastAPI.
Для методов, читающих `Request.json()` / `Request.form()`, добавлены непосредственно читаемые поля и статические списки обновления. Они отмечены `x-source-fields`.
Это **подсказки из исходников**, а не полностью верифицированные схемы: динамические поля, вложенные структуры и условные проверки могут отсутствовать; ответы многих legacy-методов пока не типизированы.
В каждой операции есть `x-handler` для точного перехода к обработчику. Не считайте эти схемы достаточными для строгой автоматической генерации всех SDK-моделей без дополнительной проверки.

Регрессионные тесты проверяют покрытие каталогом, отсутствие перекрытых маршрутов, уникальность operationId, разделение credentials, отзыв/срок ключа и прохождение штатной проверки доступа к каналу.
Они не означают, что сотни платёжных/публикующих операций выполнены на реальных клиентах: это намеренно не делается.

Перегенерация файлов без запуска БД и фоновых процессов:

```bash
pip install -r backend-python/requirements-dev.txt
PYTHONPATH=backend-python python scripts/export_api_catalog.py
PYTHONPATH=backend-python python -m unittest discover -s backend-python/tests -p test_integration_api.py -v
```

Дополнительный тест реального SQL: `RUN_INTEGRATION_DB_TESTS=1` с доступным `DATABASE_URL` и запуском `test_integration_db.py`.
Он создаёт только временные таблицы в `pg_temp` и всегда откатывает транзакцию; реальные пользователи и ключи не меняются.

На отдельном проде: обновить код, пересобрать `app`; миграция `093_integration_api_keys.sql` применяется при штатном запуске. Создавайте там отдельные ключи.
OpenAPI расширяется штатным механизмом [FastAPI](https://fastapi.tiangolo.com/how-to/extending-openapi/).
